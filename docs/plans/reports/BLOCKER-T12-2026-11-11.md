# Blocker: T12 Translate every shader on the Deck: pass rate and failure classes   (2026-11-11)

**Short version.** `hookshot --prepare-shaders` cannot finish on the Deck. It translates the first ~6,080 programs
in 42 s at about 430 MB resident. Then it reaches a block of **394 very large programs in the `Sample` archive**. With
the Deck's 4 workers each translating one, it grows to 11-13 GB in about 35 s and SteamOS's `earlyoom` kills it. This
happened three times out of three, always at the same point. The task's fallback, "re-run with fewer compile threads",
has no switch: the worker count is fixed by the CPU count. So the pass rate, the failure classes, the times and the warm
run cannot be measured as the task is written. Separately, this is a finding for T21/T24: a release build's
first-start preparation would hit the same kill on any Deck (**inferred**).

Claims are **verified** (command, file:line or log line named) unless marked **inferred** or **unknown**. The logs are
on the Deck under `~/raiders/work/` and in `work/runs/shaders1/` on the Mac, and are not committed. No shader code,
instruction words or game text are in this report.

## What the task asked

Run `hookshot --prepare-shaders` on the Deck over Raiders' census, 26,960 stages in 22,042 programs, with
`RX_VK_DUMP_FAILED`. Then:

- count lowering, translation and pipeline results;
- classify the failures with `nx2/lower_test.py`;
- compare the census with a play run;
- time a warm second run;
- report the pass rate, failure classes, time and peak memory in `M3-shaders.md`.

Step 2's pitfall reads: "if the kernel kills it, re-run with fewer compile threads (find the switch with
`grep -n "getenv(\"RX_VK.*THREAD\|JOBS" gpu/vk/*.cpp`)".

**What this means (inferred).** Each of these programs takes about 25 s on one Deck core (24.3 s, 24.2 s, 23.8 s,

take roughly 394 programs × 3 parts × 25 s / 4 workers ≈ 2 h. Whether a single one fits in memory on one worker is
**unknown**. Where the memory goes inside Eden's recompiler (the IR pools, structured control flow on a ~40k-instruction
program) is **unknown**.

### 3. There is no switch for fewer workers

- `prepare_run` starts `std::clamp(cpus / 2, 1u, 32u)` workers (`vk_draw.cpp:7350-7353`), and `warm_libraries` the
  same (`vk_draw.cpp:7184`), with `cpus = std::thread::hardware_concurrency()`. That is 4 on the Deck.
- The task's grep finds only `RX_VK_CAPTURE_THREADS` (`vk_memory.cpp:1401`), which is the capture helpers, not the
  preparation.
- `taskset` does not lower the count: a probe built in the container printed `8` under `taskset -c 0,1` and
  `taskset -c 0-3` on the SteamOS host (glibc 2.43). The probe is `~/raiders/work/t12_probe/hc.cpp`.
- So "re-run with fewer compile threads" cannot be done without a code change, and T12's scope has none.

### 4. What the partial runs did show (input for a later task, not a pass rate)

The three runs gave the same results.

**Lowering failures before the stall: 4** (log `does not lower` lines, and the 4 files in `~/raiders/work/lowfail`):

| Key | Stage | Offset | Reason (op) |
|---|---|---|---|
| `048439bbb2371e35` | 5 (compute) | +0x90 | native multiply wide addend mode (op 0x624) |
| `c6161150ded1ceb6` | 1 (fragment) | +0x77a20 | native call linkage mode (op 0x944) |
| `1d1e403c35ffbc9c` | 1 (fragment) | +0x76e90 | native call linkage mode (op 0x944) |
| `20a0a678e82aff5a` | 1 (fragment) | +0x57ca0 | native multiply wide addend mode (op 0x624) |

The three fragment failures sit at offsets of 350-490 KB, so they belong to the large programs (**inferred**). Op
0x944 is the same "CALL linkage" class Hookshot's own game still has (`docs/design.md` §9, "Open at S4").

**Other results before the stall:**

- **Translation failures: 20, all "a network left out on this card".** These are the neural-network programs. RADV
  has no cooperative matrices ("matrix multiplies in software"), so this is by design (`vk_shader.cpp:1569`).
  No other "not translated" line was logged, and the log's cap of 30 (`vk_shader.cpp:1668`) was not reached.
- **The mesh program `a393e5bb1df886f9` translated** ("mesh program …, NVN stage 7"). No task stage exists.
- **Geometry stages:** `seed_translate` builds only stages 0 and 1 of a graphics program (`vk_shader.cpp:2503-2545`).
  So the preparation never logs "dropped stages" for the 160 vertex+fragment+geometry programs. Only play does
  (`program_pick`, `vk_shader.cpp:2171`).
- **No pipeline was created in the driver** (the stage libraries come after the translation), so there are no driver
  results.
- **GPU:** `journalctl -k -b | grep -cE "gfx_|amdgpu.*timeout"` = 4, all from before T12 and none a timeout. They are
  ring set-up lines ("ring gfx_0.0.0 uses VM inv eng 0 on hub 0" ×2): two at boot and two at the S3 resume at 07:09
  (verified: `journalctl -k -b -o short-iso`). The runs added none.

### 5. The task file is out of date in places (no effect on the blocker by itself)

- **Line numbers have moved:** `program_pick` is at `vk_shader.cpp:2160` (not ~2078), the "dropped stages" log at
  `:2171` (not 2087), and the census call at `make_game.py:1712` (not 1483).
- **Wrong doc for cache keying:** `docs/pipeline-cache-save-check.md` covers save failures. The keying on the driver is
  `warmed_stamp` (`vk_draw.cpp:7096`: `pipelineCacheUUID`, vendor, device, driver version) and `prepare_check`. After
  a Mesa update only the driver's part is made again; the translations are kept (**verified** by reading; not run).
- **Log caps hide counts:**
  - Lowering failures are logged and dumped only for the first 400 programs (`vk_shader.cpp:271`), and "not
    translated" only 30 times. So `ls lowfail | wc -l` is capped at 400.
  - The summary's `failed` counts attempts, not programs: 3 per graphics program, up to 64 variants per compute program.
  - A full run would need these noted in the report, or a counting switch.
- **`$HOME` in the step 2 command is expanded on the Mac**, giving `/Users/…`. The Deck path must be written out.

### 6. Found on the way

`/tmp` on SteamOS is a RAM-backed tmpfs. It held 5.4 GB of T08a's lifter instruction test (`/tmp/a64_insn_au1ucype`:
`in.bin` and `out.bin`, 2.9 GB each, Nov 10 22:13), all of it swapped into zram. That is why the first run had no swap.
`third_party/a64-kit/tests/insn_test.py:215` makes the folder with `tempfile.mkdtemp` and never removes it, which is
an upstream (a64-kit) candidate. I moved it, without deleting, to `~/raiders/work/t12_moved_tmp/`, which frees the RAM
and keeps the files.

## What was tried

1. **Census, then the cold preparation.** Killed at 74 s with 7.5 GB, with `/tmp` full.
2. **After moving the `/tmp` leftover:** killed at 108 s with 12.2 GB.
3. **Looking for a worker-count switch:** none in `gpu/vk`, and `taskset` has no effect (section 3).
4. **A third, sampled run:** the memory curve above, and the census read by order position to find what was in flight.

Nothing in `gpu/`, `host/` or `nx2/` was changed.

## Options

1. **Measure without the large programs now; give them their own task.**
   - Now: a probe script writes a copy of the census without the 394 Sample programs over 100 KB (into `work/`), and T12
     runs on it: 21,648 programs, 4 workers, which fit at ~430 MB (verified up to position 6,080).
   - Later: a separate task deals with the 394 programs. It answers whether the game uses them (T12 step 5's seed-check
     play run, `RX_VK_SEED_CHECK=1`), measures one on one worker, and finds where the memory goes.
   - **Cost:** low; T12 finishes today, apart from the large-program class.
   - **Risk:** the pass rate leaves out ~1.8 % of programs, the ones most likely to fail (3 of the 4 failures so far are
     among them). The report must say so plainly.
2. **Add a worker-count switch** (`RX_VK_PREPARE_WORKERS=<n>` in `prepare_run` and `warm_libraries`, marked `(raiders)`,
   a generic upstream candidate). Rebuild the renderer on the Deck and run the whole census on 1 worker.
   - **Cost:** a 2-line change outside T12's scope, a renderer rebuild, and a run of about 8 h for the large block
     alone (**inferred**: 394 × 3 × 25 s).
   - **Risk:** a single large program may still exceed the Deck's memory (**unknown**).
3. **Fix the memory use of translating very large programs** in Eden's recompiler, so that the preparation (and play,
   if the game draws them) stays within the Deck's budget.
   - **Cost:** unknown: research first. It is outside T12's non-goals ("no fixes to the lowering or the recompiler").
   - **Risk:** this is the real fix for T21/T24, but it is the largest of the three.

## Recommendation

**Option 1 now, with a new task for the large programs that starts with the play run's seed check.** That task does
option 2 as its measuring tool and option 3 if the game draws them.

- **Why:** option 1 gives risk 5's number, the pass rate for 98 % of the programs, today.
- **What decides the rest:** whether the 394 programs are drawn at all. If they are not, the preparation only has to
  skip them, by size or by archive.
- **Plan impact:** T21's "prepare before the title" and T24's launcher must not run the preparation unbounded on a
  Deck as it is now. Each would be killed at the same point (**inferred** from the three runs).
