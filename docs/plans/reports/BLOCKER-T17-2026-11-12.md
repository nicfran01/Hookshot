### 2. Step 3's write-back A/B is out of date, and it does nothing on the Deck (material)

- **The ink mechanism is already known.**
  - `M4-first-frame.md` session 5 found it on 2026-11-11, after this task was written (verified, that report).
  - The game works out the ink under the player from **samples-passed occlusion counts**. These come from
    `spl::paint::ColPaint*`, one report per paint unit.
  - The enemy-ink behaviour came from the replay answering every count with a fixed 4096.
  - The fix is on `main`: `gpu/vk/vk_occlusion.cpp`, with real Vulkan occlusion queries and the switch `RX_VK_OCC_REAL`
    (verified, `vk_occlusion.cpp:136`).
  - Run `occ0` (every count 0) against `live1` (every count 4096) showed that **these counts decide the ink state**
    (verified, M4 session 5 table).
  - The two GPU buffers the CPU reads a frame later (`ink3`-`ink6`) look like a camera or visibility query, not the
    ink (**inferred** there).
- **The Deck has no write-backs to turn off.**
  - On the Deck every run logs `vk: device 0: AMD Custom GPU 0405 (RADV VANGOGH), …, type 1` and
    `vk: VRAM mirror of buffer pools off` (verified, `work/runs/occ1/hookshot_log.txt`, `work/runs/save2/hookshot_log.txt`).
    Type 1 is `VK_PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU`.
  - Mirrors are on only for discrete GPUs by default (verified, `gpu/vk/vk_memory.cpp` `mirror_on`, line 2078).
  - Write-backs are queued only for a pool whose mirror is on (verified, `vk_memory.cpp` around line 2745). Without a
    mirror the GPU writes straight into the imported guest pool (the file's header: "its writes land there").
  - So `RX_VK_NO_WRITEBACK=1` clears a list that is always empty (`vk_memory.cpp:3480`), and `RX_VK_WB_DIFF=0` changes a
    copy that never runs. **Both A/Bs would show no difference whatever the ink path is** (**inferred** from the code;
    `M3-trace.md` line 330 also shows `0.00 MB written back` on the Deck).
- **What a meaningful step 3 would be** (proposal, for you to accept or change):
  - The A/B is `RX_VK_OCC_REAL=1` (default) against `RX_VK_OCC_REAL=0` (the fixed 4096), on the scripted route.
  - The lag is the occlusion collector's latency: presents between a samples-passed report and its result being
    written (`RX_VK_OCC_LOG`, and `HOS_TRACE` around the result reader at `0x811eb380`).
  - The write-back question is kept only as a check that it does not apply: one run with `RX_VK_MIRROR=1` (mirrors
    forced on, as on a discrete card). T13 session 4's two read-back buffers are watched in that run.
  - Session 5's open points become the checks: the first ~22 reports that differ between runs, and render conditions on
    these counts.
  - Your four ink checks at the Deck stay as written.

### 3. Step 4: "Game speed = Real time" and `HOS_FPS_LOG` are Ocarina's (not material: the step shrinks)

- **They need Ocarina's graphics module.**
  - `realtime_step` and the `HOS_FPS_LOG` line both work on `hos_gfx_module` (verified, `host/nn_vi.c` from line 205,
    and line 315 `if (!mod) return;`).
  - That module is found only when `GetSystemTick` returns to Ocarina's address `0x8348c770` (verified,
    `host/hos_thread.c:1007`). The fields written (`+0x2c8`, `+0xfc`) are Ocarina's engine.
- **So for Raiders** neither the menu row nor the log does anything, unless Raiders happens to call `GetSystemTick`
  from that same address (**unknown**).
- **The hook is not gated on the game id.**
  - CLAUDE.md says Ocarina code is gated on the game id, and `docs/design.md` §4 says a hook is never kept "by address
    coincidence".
  - If the address does match in Raiders, the hook writes into a Raiders object every present. T07 left this hook
    ungated. Checking the address in Raiders' image is a research step, and gating the hook would be a small fix.
- **What step 4 can measure:** whether Raiders slows below its target, by a stopwatch against an in-game timer.
  Raiders' own target needs another source than `HOS_FPS_LOG`. T13 measured ~31-33 fps in play
  (`M4-first-frame.md`, `occ1`).
