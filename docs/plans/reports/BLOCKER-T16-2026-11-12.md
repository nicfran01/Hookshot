### Done: commit atomicity (step 5): not atomic, an upstream issue

- `nn::fs::Commit` is `RET(0)` (`host/nn_fs.c:311`), here and on `upstream/main` (verified).
- `WriteFile` writes straight into the host file at the guest's offset (`nn_fs.c:437`).
- `FlushFile` is `fdatasync` on Linux (`host/posix/win32_posix.c:930`).
- **So a save is not atomic.** If the process dies or the power goes during a write, `save.dat` can be left half old and
  half new.
- An atomic commit would need copy-on-write. One way: the save mount writes to a shadow copy, and `Commit` renames it into
  place. The task says not to redesign it here. **A candidate upstream issue.**

### Blocked: the round trip (scope 2)

1. **The script is cut at 511 characters** (verified).
   - `run.sh` writes each `-- NAME=VALUE` into `env.txt`, which the game reads through `HOS_ENV_FILE`.
   - That reader takes lines of at most 511 characters (`char line[512]`, `host/hos_main.c` `load_hookshot_env`; the same on
     `upstream/main`).
   - The cut is silent. T13's `play1` and `ngc1` scripts ("A to 598 s", "A to 418 s") were really cut to
     `hid: input script of 87 presses (last at 206 s …)` (`work/runs/play1/hookshot_log.txt:1291`). The figures in
     `M4-first-frame.md`'s tables are what was asked for, not what ran.
2. **From an empty save folder the game is much longer than T13's runs.** T13's runs started from a save past the opening;
   `play1`'s screenshots go from the clouds straight to the hub.
   - From empty (verified, `save1` screenshots and `vi:` lines): clouds, "Select a difficulty", the autosave notice
     ("Start!" writes `save.dat`, 28-33 s in), then the in-engine opening.
   - The opening runs ~180 s at ~31 fps and seems to need no input: it ended at the same point with A every 2 s and
     every 6 s (inferred).
   - Then the hub, and **character customization from ~207 s** (present ~8,100).
3. **Customization needs RIGHT before A at its last step** (verified, screenshots).
   - The prompt "Looking good? Happy with this?" has its cursor on "Hold Up…", which goes back to the eyes step.
   - "Love it!" is to its right.
   - A pressed alone loops the steps; so does `A+RIGHT` in one press (the game takes the A first).
4. **Where the progress save is.**
   - T13 found that the save the game honours is written after the hub's first scene and its loading screen, not at
     "Start!" (`M4-first-frame.md`, session 2).
   - From empty, that is after customization plus the hub dialogue: about 100 s of A presses in `play1`'s screenshots.
   - Each step needs about 6 characters of script for an A and about 10 for a RIGHT. Covering 200-400 s at a usable rate
     (an A every 2-4 s, a RIGHT before each) takes 600-800 characters. The cap leaves 494.
   - The save is probably after 400 s anyway (inferred: ~207 s plus customization plus ~100 s of dialogue plus loading).

## Options

1. **Lift the 511-character cap and give `save1` more time.**
   - Raise `load_hookshot_env`'s line buffer (for example to 8 KiB, with a test that a long `HOS_INPUT_SCRIPT` survives).
   - Write `save_and_quit.txt` as A every 2 s with a RIGHT before each A from ~200 s.
   - Run `save1` for about 600 s instead of 400 s.
   - **Cost:** one small generic change to an upstream file (also a candidate upstream PR, CLAUDE.md), one Deck build
     (~3.5 min), one or two runs.
   - **Risk:** the progress save's time from empty is still **unknown** (it may need more than 600 s or more presses).
     It also changes the acceptance command's time limit.
2. **Keep the code as it is and send the presses through `HOS_INPUT_LIVE`.**
   - Before the run, write the press file to `~/raiders/work/live.txt` on the Deck (one `ssh … 'cat > …'`).
   - `live_input()` reads lines of up to 4,095 characters, timed from when they are read (`host/nn_hid.c`, `live_input`).
   - **Cost:** no code. The acceptance command changes from `HOS_INPUT_SCRIPT=…` to `HOS_INPUT_LIVE=<file>`, plus a step
     outside `scripts/deck/*.sh`.
   - **Risk:** the same unknown time to the progress save. The 400 s limit probably still has to grow.
3. **Start `save1` from a copy of a progress save.**
   - Copy your title save (`~/raiders/work/t15_save_title/`) into `runs/save1/user/save/<id>/`.
   - Use T15's `new_game.txt` to reach the hub, then wait for or trigger the next autosave.
   - **Cost:** needs T15 merged first. Runs are short, since there is no opening and no customization.
   - **Risk:** "create save data" is no longer tested, because the file exists. Whether the hub autosaves within
     400 s is **unknown**.

## Recommendation

**Option 1.** It keeps the round trip honest: an empty folder, created by the game, then written, quit, started and
loaded. It also fixes a silent cut that has already misled T13's reports. The time limit has to grow with it, and that
choice is yours.

**If you want no change to upstream files in T16, option 2.** The other half of T16 (scope 1, scope 3, step 5) is
committed either way.
