# Blocker: T10 Offline answers for network, local wireless, amiibo, friends, keyboard   (2026-11-10)

## What the task asked

Implement `HLE()` answers in a new `host/nn_offline.c`, "for the functions the trace marked wrong or blocking", in these
namespaces: `nn::ldn`, `nn::nfp`, `nn::friends`, `nn::swkbd`, `nn::nifm`, `nn::socket`/`nnsocket*`/`nn::ssl`,
`nn::account` network-token calls, `nn::prepo` and `nn::err`. Then build and run `offline1` on the Deck, and show with
`scripts/trace_report.py` that no entry in these namespaces is still "wrong answer" or "blocking". Its non-goal says:
"Do not implement functions the trace never saw unless they are in the same small family as one it did."

## What was found

1. **The trace saw no function in T10's namespaces** (verified: `docs/plans/reports/M3-trace.md` on
   `task/T09-trace-report`, `571dc27`, §1 and "Stubs called"). Before the stop, the game called exactly 3 generated stubs:

   | Stub | Class (T09) | In T10's namespace list? |
   |---|---|---|
   | `nn::ro::ProtectRelro` | safe | no |
   | `nn::hid::InitializeJcms` | safe | no (`nn::hid`, T15) |
   | `nn::pl::GetBuiltInFontData(BuiltInFontDataOunce*, BuiltInFontTypeOunce, bool)` | **blocking** | **no** (`nn::pl`) |

   Both trace runs (`trace1`, and `trace2` with `HOS_NVN_STRICT=1`) stop at log line 819, on the null read right after
   that font stub. No submit and no present come before it (verified there).
2. **The only blocking call is outside T10's scope.** M2-boot.md and M3-trace.md both hand `GetBuiltInFontData` to
   T10. But T10's Scope, its behaviour table and its acceptance `grep -E "ldn|nfp|friends|swkbd|nifm|socket|ssl"` all
   leave out `nn::pl`. No other task covers it: `grep -il font docs/plans/tasks/*.md` only finds T05 (the in-game menu
   font) and T25.
3. **As written, T10 cannot do what it is for.**
   - Its scope picks nothing: there is no wrong or blocking call in its namespaces.
   - If the table were applied without the trace, the work would break its own non-goal. That is 26 + 23 + 6 + 7 + 9 +
     32 + 2 + 2 + 3 + 1 = 111 stubbed imports, counted by namespace in `work/standalone_stubbed.txt`. None of them has a
     caller seen at run time, and none has a "read the caller's comparison" result-code check, which step 1 requires.
   - The acceptance grep would pass trivially: no line matches before or after.
   - `offline1` would stop at the same font crash, so the report's "what the game does next in the boot" would be
     unchanged.
4. **The font fix is not a small add-on.** The caller passes a struct on its own stack, ignores the result, then returns
   the struct's pointer field and stores its size field (M2-boot.md, verified there by disassembly). A failure result
   therefore does not help (**inferred**): the game needs a pointer to font data it can use.
   - What format the game expects from the Ounce built-in font is **unknown**: the struct's full layout, and whether
     it wants a raw TrueType/OpenType file or a console container.
   - The runtime already answers the older `nn::pl::GetSharedFont*` with an empty, "loaded" font
     (`host/nn_applet.c` "nn::pl: system shared fonts"). It has nothing for `GetBuiltInFontData` (`work/standalone_stubbed.txt`
     lists both overloads, Nx and Ounce, and `nn::pl::RequestLoadNxFont`).
   - The repository already carries OFL fonts that a stand-in could use: `third_party/fonts/libertinus/LibertinusSans-*.ttf`
     (readme: the menu's included font) and Inter in `builder/`.
5. **Branch base.** T10 depends on T09, and `task/T09-trace-report` is not merged into `main` (verified: `git branch
   --merged main`). This branch starts from `main` at `6b68684`, so it has neither `scripts/trace_report.py` nor
   `M3-trace.md`, both of which T10's step 4 and acceptance use.

## Options

1. **New task before T10: "built-in font stand-in" (`nn::pl::GetBuiltInFontData`, both overloads, and
   `RequestLoadNxFont`). Then T10 runs on the next trace.**
   - Cost: a research step and one HLE. The research is the struct layout and the format the caller hands to the font
     engine: disassemble the caller and the consumer of the returned pointer on the Mac, as M2 did.
   - Then: serve an included OFL font, or an empty font if the engine copes, plus a Deck run.
   - Risk: the game's text engine may need glyphs or a container format that a stand-in does not give. Then the
     options are an empty-font answer that the engine skips, or a narrow patch.
   - T10 keeps its rule (trace first), and its acceptance becomes meaningful.
2. **Widen T10 to take the font call as its first step, then the offline answers the following trace shows.** The
   same work as option 1 in one branch. Cost: a larger, less reviewable task. Risk: the scope keeps growing as the
   boot goes further.
3. **Do T10 as written, without trace evidence: the behaviour table for all 111 imports.**
   - Cost: large.
   - Risk: high. Result codes would be guessed, which the task's own pitfall forbids. The work breaks the non-goal, and
     nothing at run time checks it until the game gets past the font.
   - Not recommended.

Independently of the option: merge `task/T09-trace-report` into `main` first (as was done for T07 and T08), so the T10
branch has `scripts/trace_report.py`.

## Recommendation

**Option 1.** Merge T09 into `main`. Add a font-stand-in task between T09 and T10 (owner of `GetBuiltInFontData`, with the
research step above and a Deck run that shows the boot getting past line 819). Then rerun the trace and redo T10 against
the calls it shows. T10's scope rule, behaviour table and network guard (step 5) can stay as written. Planning should also
decide whether the network guard (step 5, a `connect()` check) should move earlier. It costs little, protects
constraint 3 from the first run that reaches the network code, and does not depend on the trace.
