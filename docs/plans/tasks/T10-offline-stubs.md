**Milestone:** M3 (Part A), then repeatable (Part B) · **Depends on:** T09a (the boot is past the font stop
and `docs/plans/reports/M3-trace.md` was regenerated from that run) · **Machine:** Mac driving the Deck

## Context
Raiders links NPLN, Pia (online, local, LAN), `nn::ldn`, `nn::nfp`, `nn::friends`, `nn::swkbd`. The project
is offline by constraint (`CLAUDE.md` constraint 3). The runtime must make the game see a console with no
network, no local wireless partners, no amiibo activity and no friends, and must never reach a network.
Hookshot already gives offline answers for its own game's NPLN path (`docs/design.md` §9). Generated stubs
return 0, which for many of these functions means "success" and is the wrong answer.

The first trace (T09) showed **no call in any of these namespaces** before the boot stopped at the built-in
font (now T09a). So which answers the game needs is still unknown, and may stay unknown until the title
screen or a menu. Writing all 111 stubbed imports of these namespaces without a caller to check against would
mean guessing result codes, which this task forbids.

## Part A · Offline guard (unconditional; do this first, once)

It does not depend on the trace and protects constraint 3 from the first run that reaches network code.

1. **Source check.** `tests/test_no_network.py` (game-free): scans `host/` and `gpu/vk/` (not `third_party/`)
   for calls that open network connections (`socket(`, `connect(`, `getaddrinfo(`, `sendto(`, `WSAStartup`,
   `curl_`), and fails on any outside an allowlist. The allowlist starts with `host/discord_rpc.c` (local
   IPC only) and every entry carries a reason. This catches an upstream merge that adds networking.
2. **Discord presence off for this game.** `discord_rpc.c` announces the game to the user's Discord client
   under upstream's application. For any game other than upstream's it must be off by default: gate it on the
   game config (a `DISCORD_PRESENCE = False` field in `games/raiders/game.py`, read through the generated
   game identity as T07's gates are), with the existing option still able to turn it on. Read the file first
   to see what already decides whether it runs.
3. **Run-time check.** `scripts/deck/run.sh` gains `--net-check`: while the game runs it samples the
   process's sockets every 5 s (`ss -tunpH` filtered by pid, or `/proc/<pid>/net` and `/proc/<pid>/fd`
   socket links if `ss` is missing on SteamOS: check which exists) and writes
   `work/runs/<name>/net.txt`. Any TCP or UDP socket with a non-loopback peer is a failure line. Unix-domain
   sockets (Wayland, PipeWire, D-Bus) are expected and listed but not failures.
4. Confirm by reading that `nn::socket`'s lifted code cannot reach the host: the `sdk`'s socket functions end
   in IPC to `bsd:u`/`sfdnsres`, which the runtime answers itself (`ConnectToNamedPort` in `host/hos_svc.c`).
   State in the report what answers them and with what.

## Part B · Offline answers (trace-driven; repeat when a trace shows new calls)

**Trigger:** the current `M3-trace.md` (or a later trace from T13, T15, T17) lists a call classed "wrong
answer" or "blocking" in one of this task's namespaces. **If it lists none, Part B has nothing to do:** say so
in the report with the trace's "end:" line as evidence, finish the task with Part A, and leave Part B open.
The session that later meets such a call (most likely T13 or T15) runs Part B then, as its own short session.

`host/nn_offline.c` (new), holding `HLE()` implementations for the triggering functions and the rest of their
small family (for example every `nn::ldn` state getter once one `nn::ldn` call is seen).

Behaviour:

| Area | Answer |
|---|---|
| `nn::nifm` | Initialise succeeds; network not available; requests complete immediately with "not connected" |
| `nn::socket`, `nn::ssl` | No function reaches the host's network stack. Creation fails or `Poll`/`Select` report nothing ready, matching what exists upstream |
| `nn::ldn` | `Initialize`/`Finalize` succeed; state stays `None`/`Initialized`; `Scan*` returns 0 networks; `CreateNetwork`, `Connect*` return a failure result; `GetNetworkInfo`/`GetIpv4Address` fail; the state-change event is created and never signalled |
| `nn::nfp` | `Initialize` succeeds; `ListDevices` returns 0 devices; device-state queries say "unexpected/none"; events created, never signalled |
| `nn::friends` | Empty friend list; presence calls succeed and do nothing |
| `nn::swkbd` | `ShowKeyboard` returns the "cancelled" result; size queries return plausible fixed sizes |
| `nn::account` network token / NSA id | Fail as upstream does for `EnsureNetworkServiceAccountIdTokenCacheAsync` |
| `nn::prepo` (play reports), `nn::err` (error viewer) | Succeed and do nothing; log the error code once for `nn::err` |

Steps for Part B:
1. For each function, take the exact mangled name from `work/standalone_stubbed.txt` and write the `HLE()`
   with a one-line comment giving the demangled signature and the answer.
   - Pitfall: an `HLE()` is picked up at lift time, so adding one relifts on the Deck (T08: 2,544 s). Batch
     the additions per iteration.
   - Pitfall: result codes. Do not invent module/description numbers. Read the caller's comparison (the
     traced `lr` gives the caller; disassemble it on the Mac as M2 did) and return what makes it take its
     "not available" branch. Record each finding in the report by function name.
   - Pitfall: out-parameters (counts, handles, info structs) must be written (zeroed) even on failure.
2. Add `nn_offline.c` to the host sources in `nx2/build.py` for Linux and Windows.
3. `tests/test_nn_offline.py` in upstream's style, covering each implemented family.
4. Build, run, regenerate the trace report; no entry of these namespaces may remain "wrong answer" or
   "blocking".
